# ADR 0001: Stack: static Astro on Cloudflare Pages with Pages Functions, D1, Access and a git-based CMS

- Status: Accepted (stack chosen by the owner on 2026-10-24, see `docs/brief.md` header). The refinements below are architect decisions. Owner questions are listed at the end.
- Date: 2026-10-24
- Supersedes: brief §10 "Recommended architecture" (Next.js, Prisma, PostgreSQL, next-intl, shadcn/ui). §10 allows Cloudflare as an alternative.
- Related: `docs/architecture.md`, `docs/ia.md`, `docs/plan.md`

Versions below were read from the npm registry on 2026-10-24. Developers pin exact versions at scaffold time and commit the lockfile.

## Context

The brief (§1–§18) requires:
- a multilingual marketing site (SK default, CS, EN)
- two forms that store data and send emails
- a secure admin with statuses, notes, CSV export, retention deletion and an audit log
- an editor CMS, a blog and SEO
- Lighthouse scores of 90 for performance and 95 for accessibility and SEO, WCAG 2.2 AA, and GDPR-aware handling of parent and child data

The owner chose a Cloudflare-native stack and deploys with the `cf-pages-deploy` skill. That skill runs `wrangler pages deploy` and needs one approval per deploy.

Facts that shape this ADR:
- **F1.** `@astrojs/cloudflare` dropped official Cloudflare Pages support in v13.0.0 and now targets Workers only (changelog PR withastro/astro#15480). The current version is 14.4.2 and requires `astro ^7.4.0`.
- **F2.** Pages Functions support D1, KV, Durable Objects, R2, Queues producers, Analytics Engine, service bindings, variables and secrets. They have **no Rate Limiting binding** and **no cron triggers** (Cloudflare docs, "Pages Functions bindings").
- **F3.** `_headers` rules **do not apply to responses generated by Pages Functions**. The file allows at most 100 rules and 2,000 characters per line. `! Header` detaches an inherited header (Cloudflare docs, "Pages headers").
- **F4.** Astro's `security.csp` (since 6.0) emits a per-page `<meta>` CSP with hashes. It is not available in `astro dev`, and a meta policy cannot express `frame-ancestors`.
- **F5.** D1 supports `--jurisdiction=eu`, which runs and stores data only in the EU. The jurisdiction can only be set when the database is created (Cloudflare docs, "D1 data location").
- **F6.** Cloudflare Email Sending is in beta, requires Workers Paid, and its docs do not mention Pages Functions.
- **F7.** Sveltia CMS:
  - has first-class i18n
  - signs in to GitHub with a token or through an OAuth client (PKCE is not implemented for GitHub)
  - requires editors to have GitHub write access
  - can be self-hosted from npm
  - needs `style-src 'unsafe-inline'` on its own page (sveltiacms.app docs, security and GitHub backend)

## Decisions

### D1. Astro 7.x, static output, no adapter, on Cloudflare Pages
- **Decision:** Astro 7.x with `output: 'static'` and no adapter. `build.format: 'directory'`, `trailingSlash: 'always'` and `build.inlineStylesheets: 'never'`.
  - Every public page, the localized 404 pages, `/admin/` (an empty app shell) and `/cms/` are prerendered static files.
  - All dynamic behaviour lives in hand-written **Pages Functions** under `functions/`.
  - `_routes.json` sends only `/api/*` to Functions, so static pages never invoke a Function.
- **Rejected:**
  - (a) `@astrojs/cloudflare` 14 on Workers with hybrid rendering. It is Cloudflare's recommended path for new projects, but it conflicts with the owner's Pages deploy skill. It would need a new deploy procedure plus a Workers approval each time (F1).
  - (b) Astro 5 with adapter 12, the last version that supported Pages. It pins us to an outdated major version.
  - (c) Hand-rolled SSR. No route needs request-time rendering.
- **Consequences:**
  - There is no SSR anywhere, which keeps the site fast and cache-friendly.
  - Handlers are plain `(request, env, ctx) => Response` functions in `src/server/`, and `functions/` only wraps them. If Pages is later retired, moving to Workers static assets only means replacing those wrappers with a router.
  - Security headers for API responses must be set in code (F3).

### D2. Islands with Preact 10.x
- **Decision:** Preact 10.x through `@astrojs/preact` 6.x, with ~~`@preact/signals`~~ plain hooks for form state. Islands are mounted without Astro `client:*` directives, by an external module (amendment A4.1, which supersedes the directives below). The islands are:
  - `ContactForm` and `EnrollmentForm` (~~`client:visible`~~ hydrated on load)
  - `FaqSearch` (~~`client:idle`~~; prefer a plain module, A4.1)
  - `AdminApp` (~~`client:only="preact"`~~ rendered by a mount module, on `/admin/` only; until then `client:only` with the strip hook, A4.1)
  - the consent banner, only if GA4 is ever chosen (D12)

  Mobile navigation uses `<details>` or a tiny external module script, not an island. JS budgets:
  - pages without forms: at most 10 KB gzip
  - form pages: at most 35 KB gzip
  - `/admin/`: at most 80 KB gzip

  A CI size check enforces them.
- **Rejected:**
  - React with React Hook Form (brief §10): about 4x the runtime size, which threatens Lighthouse 90+ on mid-range mobile.
  - Svelte and Solid: also small, but Preact keeps JSX familiar to the agents and has mature testing-library support.
  - Preact 11.0: released 2026-09-30. Too new; revisit in Phase 8.
- **Consequences:**
  - Form controls are Preact components that share CSS classes with the Astro design-system components (see "Constraints for design" in `docs/architecture.md`).
  - Forms render server-side at build time, so their HTML exists without JS (progressive enhancement, D7).

### D3. Shared validation with Zod 4 (`zod/mini`)
- **Decision:** One schema per form in `src/shared/schemas/`, written with `zod/mini` (Zod 4.x, tree-shakable). Islands and Functions import the same module.
  - Schemas emit stable **error codes** (for example `required`, `email_invalid` and `too_long`), never human text.
  - The UI and the server map codes to localized messages from the i18n dictionaries.
  - The server also normalizes input: trim, Unicode NFC, lowercase email, and strip control characters.
  - Enumerations (regions, subjects, grades, statuses, next steps) live in `src/shared/enums.ts` and are mirrored as SQL `CHECK` constraints.
- **Rejected:** full `zod` on the client (larger bundle), Valibot (smaller, but the brief names Zod and `zod/mini` closes most of the gap), and separate client and server schemas (they drift).

### D4. D1 in the EU jurisdiction, plain SQL migrations, no ORM
- **Decision:**
  - **Databases:** one D1 database per environment (`domo-skola-prod`, `domo-skola-preview`), created with `--jurisdiction=eu` (F5). Local development uses Miniflare's local D1.
  - **Migrations:** plain SQL files in `migrations/NNNN_name.sql`, applied with `wrangler d1 migrations apply`. They are forward-only, and each migration has a test that applies it to a fresh local database.
  - **Data access:** a small typed repository layer in `src/server/db/` that uses `prepare().bind()` only. String-built SQL is forbidden by lint. Rows are parsed with Zod at the boundary.
  - **Integrity:** multi-statement writes use `db.batch()` and rely on foreign keys with `ON DELETE CASCADE`.
- **Rejected:** Drizzle and Prisma. Seven small tables do not justify a second schema source, a generator and extra bundle weight. Postgres through Hyperdrive was rejected as an extra processor plus connection management for no gain.
- **Consequences:** the jurisdiction is a one-time decision, made when the production database is created in Phase 8. Owner approval is needed because a binding is a separate yes under `cf-pages-deploy` §0.

### D5. Email: EU-based provider behind a transport interface; first adapter Brevo
- **Decision:** `src/server/email/transport.ts` defines `send({to, from, replyTo, subject, text, html, tag})` and calls an HTTP API with `fetch` (no SMTP from Workers). Adapters:
  - `brevo`: the default recommendation, an EU company (France)
  - `scaleway`: alternative, Scaleway Transactional Email (France)
  - `mock`: posts to a local capture server for development and e2e

  Before launch the owner confirms the provider's processing location and signs its DPA.

  Email rules:
  - Each email has a plain-text and a minimal-HTML body.
  - Templates are localized (D11).
  - **No user-supplied free text, names or child data appear in confirmation emails.** This keeps the form from being abused as a spam relay to arbitrary addresses and follows brief §7 ("avoid unnecessary child-related details").
  - Admin notifications carry only the record type, locale, region, subject or next step, and a link to the admin record. Reply-To is the submitter's address.
  - Emails are sent after the D1 commit, in `ctx.waitUntil`. Each send writes an `email_deliveries` row with a status, so an email failure never loses a submission. The admin can resend, and the resend is audited.
  - Sending needs SPF, DKIM and DMARC on the sending domain.
- **Rejected:**
  - Cloudflare Email Sending: beta, Workers Paid only, and Pages Functions support is undocumented (F6). Revisit when it is GA.
  - Resend and Postmark: US companies, which would add a third-country transfer analysis. They can be added as adapters if the owner prefers.
  - MailChannels Workers relay: its free tier for Workers is understood to have ended in 2024 (not re-verified here). Do not rely on it.

### D6. Rate limiting and anti-spam: layered; Turnstile off by default
- **Decision**, in order inside each public handler:
  1. Method, `Content-Type` and body-size check (at most 32 KB).
  2. Origin check (D7).
  3. **D1-backed fixed-window limiter.** The key is HMAC-SHA256(IP, `IP_HASH_SECRET`) plus the route. Defaults, all configurable: 5 per 10 minutes and 20 per day per IP. The recipient address is also limited (HMAC of the email, 3 confirmations per day) to prevent mail-bombing. Over that limit the submission is still stored and only the confirmation is skipped (amendment A2). Rows expire after 24 hours.
  4. **Honeypot field.** A hit returns a fake success and nothing is stored or sent.
  5. **Minimum fill time.** The island sends `elapsedMs`, the time from mount to submit measured with the client's monotonic clock (`performance.now()`); client and server wall clocks are never compared, so a skewed device clock cannot flag a real parent. If the form was filled in under 3 seconds, the record is stored with `suspected_spam = 1` and no confirmation email is sent. The no-JS form cannot measure time and sends no value (treated as unknown, not suspected); a JSON request without a positive `elapsedMs` is suspected, because the island always sends one. (Amended at the L5a sign-off, 2026-10-24; it replaces the earlier `renderedAt` render timestamp.)
  6. **Content heuristics.** More than 3 URLs in the free text marks the record as suspected.

  One Cloudflare WAF rate-limiting rule on `/api/*` adds coarse burst protection at the edge (zone setting, Phase 8).
- **Turnstile:** implemented behind `PUBLIC_TURNSTILE_SITE_KEY` (empty means off). Turn it on only if the measured spam that gets past layers 3–6 exceeds an agreed threshold. Costs:
  - The form pages' CSP must add `script-src` and `frame-src` for `https://challenges.cloudflare.com`, scoped to those paths in `_headers`.
  - Forms stop working without JS.
  - The privacy notice must list Cloudflare's processing of browser signals for bot detection.
- **Rejected:** Turnstile always on (privacy, CSP surface and a11y friction for a low-traffic site), reCAPTCHA or hCaptcha (third-party tracking, cookie implications), and the Workers Rate Limiting binding (not available on Pages, F2).
- **Consequences:** a hashed IP is pseudonymous personal data. It is kept for 24 hours at most and listed in the privacy notice.

### D7. CSRF and request integrity
- **Public endpoints** (`/api/contact`, `/api/applications`) use no cookies or ambient credentials, so classic CSRF does not apply. Two checks still run:
  - an **`Origin` allowlist** (`ALLOWED_ORIGINS`), which rejects cross-site posting abuse
  - `Sec-Fetch-Site` must be `same-origin` when present

  Both `application/json` (island) and `application/x-www-form-urlencoded` (no-JS fallback, which answers 303 to the localized success or error page) are accepted.
- **Admin endpoints** (`/api/admin/*`) carry the ambient Access cookie, so they enforce:
  - mutations are `POST`, `PATCH` or `DELETE` with `Content-Type: application/json` only. These are non-simple requests that need a CORS preflight, and no CORS headers are ever sent.
  - `Origin` must equal `SITE_URL`
  - `Sec-Fetch-Site: same-origin`
  - `GET` has no side effects. CSV export is a `POST` whose response is saved as a blob by the SPA.
- **Rejected:** synchronizer tokens. A static site has no session to bind them to, and the checks above cover the threat model.

### D8. Admin: a small custom admin behind Cloudflare Access; roles in D1
- **Decision:** `/admin/` is a static shell plus the `AdminApp` Preact SPA. It calls JSON APIs under `/api/admin/*`.
  - **Access:** one Cloudflare Access application protects `/admin*`, `/api/admin*` and `/cms*` on the production custom domain, on `<project>.pages.dev` and on `*.<project>.pages.dev` (preview deployments).
  - **JWT check (defense in depth):** every `/api/admin/*` request is verified in `functions/api/admin/_middleware.ts`. The `Cf-Access-Jwt-Assertion` header is checked with RS256 against the team JWKS (`https://<ACCESS_TEAM_DOMAIN>/cdn-cgi/access/certs`, cached) using the `jose` library, along with `aud == ACCESS_AUD`, `iss` and `exp`. A missing or invalid JWT gets a 401.
  - **Roles:** **Access answers "who may enter", D1 answers "what they may do".** The verified `email` claim is looked up in the `admin_users` table (`role`: `admin` or `coordinator`). An email that is not listed, or is disabled, gets a 403.
  - **Permission matrix:** see `docs/architecture.md`. Every change, every export, every deletion and every detail view writes `audit_log`.
- **Rejected:**
  - Roles from Access groups: needs an identity provider with group claims and a call to `get-identity`. Possible later as an optional mapping.
  - A headless CMS holding submissions: puts parent and child PII in git or a third-party SaaS.
  - The D1 console as the admin: no roles, no audit, no CSV safety.
  - Retool and similar tools: another processor for child data.
- **Consequences:**
  - `admin_users` is managed with documented `wrangler d1 execute` commands in v1. These changes are outside the app's audit log, which is documented.
  - Local development and e2e use a mock JWKS and a dev proxy that injects a signed test JWT. **No auth bypass exists in Function code.** The preflight check fails if `ACCESS_CERTS_URL` is set in production.

### D9. CMS: Sveltia CMS, self-hosted at `/cms/`, GitHub backend, OAuth handled by our own Functions
- **Decision:** Sveltia CMS (`@sveltia/cms`, 0.x) is copied from `node_modules` into `dist/cms/` at build time. There is no CDN. It edits Markdown and JSON in `src/content/`.
  - **i18n:** `structure: multiple_folders` for collections (`<collection>/<locale>/<slug>.md`) and `single_file` for site settings. Fields are marked `i18n: true` or `i18n: duplicate`.
  - **Sign-in:** a GitHub OAuth app. The token exchange runs in two Pages Functions, `/api/cms-auth/auth` and `/api/cms-auth/callback`, ported from the MIT-licensed `sveltia-cms-auth` with attribution. They are restricted to the site origin and `GITHUB_OAUTH_CLIENT_SECRET` stays server-side.
  - **Protection:** `/cms/` also sits behind Access.
  - **Editorial workflow:** on. Each edit opens a PR, and a merge to `main` plus an approved deploy publishes it.
  - **Consistency:** a check tool (`tools/check-cms-config.mjs`) fails CI if `public/cms/config.yml` and `src/content.config.ts` disagree on collections or fields.
- **Rejected:**
  - Keystatic: GitHub mode needs SSR API routes and React, which conflicts with D1 (no adapter).
  - Decap CMS: weaker i18n and slower maintenance. Sveltia is a compatible successor with first-class i18n.
  - A hosted headless CMS (Storyblok, Sanity): another processor, a runtime fetch or build webhook, and cost.
- **Consequences:**
  - Editors need GitHub accounts with write access (F7).
  - **CMS edits are not live** (see Gaps).
  - Sveltia is pre-1.0, which is a risk. Its config is Decap-compatible, so Decap is a fallback.
  - `/cms/*` gets its own CSP with `style-src 'self' 'unsafe-inline'` (F7). It is scoped to that path and never applied to public pages.

### D10. Styling: plain CSS with custom-property tokens
- **Decision:**
  - Design tokens live in `src/styles/tokens.css` as CSS custom properties, delivered by the design lane (`docs/design/`).
  - Components use Astro scoped styles and global utility classes, compiled to external files (`inlineStylesheets: 'never'`).
  - There is no runtime CSS-in-JS and no `style=""` attributes.
  - Motion is CSS-only and honours `prefers-reduced-motion`. Astro `<ClientRouter />` is not used: it is incompatible with Astro CSP (F4) and costs JS.
- **Rejected:** shadcn/ui (React-only), Motion (runtime JS) and Tailwind as the default. Tailwind v4 is acceptable if the design lane asks for it, because it compiles to static CSS and is CSP-safe; record that as an amendment to this ADR.

### D11. i18n: Astro i18n routing, translated slugs, namespaced JSON dictionaries
- **Decision:**
  - Astro `i18n` with `locales: ['sk','cs','en']`, `defaultLocale: 'sk'` and `routing.prefixDefaultLocale: true`. `/` redirects 301 to `/sk/` through `_redirects`.
  - **Slugs are translated per locale** (justified in `docs/ia.md` §1). A route map `src/i18n/routes.ts` maps page key → slug per locale. Every page, the language switcher, hreflang and the sitemap use it.
  - UI strings live in `src/i18n/ui/<locale>/<namespace>.json`. Namespaces: `common`, `nav`, `forms`, `validation`, `email`, `admin`, `seo`, `status`. SK is the source of truth, and a unit test fails on any missing or extra key in CS or EN.
  - **Email templates** are TypeScript functions in `src/server/email/templates/` that take `(locale, dictionary, data)` and import the `email` namespace, so wrangler bundles them into Functions.
    - The confirmation email is sent in the submitter's language: the page locale for contact, and `preferred_language` for enrollment.
    - Admin emails use `ADMIN_EMAIL_LOCALE` (default `sk`).
  - Admin UI strings ship in SK and EN.
- **Rejected:** `astro-i18next` and Paraglide (extra build tooling for three locales), and English slugs everywhere (see `docs/ia.md`).

### D12. Analytics: off by default; recommended Plausible-compatible cookieless analytics through a first-party proxy; GA4 only through the `consent-analytics` skill
- **Decision:**
  - `PUBLIC_ANALYTICS_PROVIDER` takes `none` (default), `plausible` or `ga4`.
  - **`plausible`:** the tracker script is served from `/js/`. Events go to `/api/e`, a Function that forwards to the provider, so the CSP stays `'self'`. No cookies. A fixed event enum carries enum properties only (`docs/ia.md` §3).
  - **`ga4`:** follows the `consent-analytics` skill exactly: opt-in banner, Consent Mode v2 defaults denied, external bootstrap file, path-scoped CSP. It never runs on `/admin/`, `/cms/` or inside form islands beyond a submit-success event.
- **Rejected:**
  - Cloudflare Web Analytics: no custom events, so it cannot measure the §13 funnels, and its auto-injected beacon conflicts with the hash CSP.
  - Our own Analytics Engine pipeline: no dashboard for the owner without extra work.
- **Consequences:**
  - Whether cookieless analytics needs consent under SK and CZ ePrivacy law is a **legal-review item**.
  - The privacy page lists the provider and its processing in either case.

### D13. Security headers and strict CSP from `_headers`, with build-time hashes
- **Decision:**
  - **Generation:** `tools/build-headers.mjs` runs after `astro build`. It reads `config/headers.template`, scans `dist/**/*.html`, computes SHA-256 hashes for every executable inline `<script>` and writes `dist/_headers`. Islands are mounted by external modules (A4.1), so no page should need a hash. Today's only hashes are the Astro runtime scripts on `/admin/`, until the admin moves to a mount module. After that the limit becomes 0 (A4.4).
  - **Fail conditions:** the build fails on any inline `<style>`, any `style=` attribute, any inline event-handler attribute, any external origin, or more than 6 distinct inline-script hashes. JSON-LD `type="application/ld+json"` blocks are data and are exempt.
  - **Why not Astro's `security.csp`:** it is not enabled, because a second, meta policy would intersect with the header (F4).
  - **Functions:** `functions/_middleware.ts` sets the same headers on every Function response (F3), plus `Cache-Control: no-store`.
  - **Path classes:** public, `/admin/*`, `/cms/*`, and form pages if Turnstile is on. The policies are listed in `docs/architecture.md` §8.
  - **Trusted Types:** ~~trialled on `/admin/*` in Phase 7~~ the L7 trial had zero violations, so `require-trusted-types-for 'script'` is enforced on `/admin/*` as one replaced policy (A4.3).
- **Consequences:** the "Constraints for design" in `docs/architecture.md` follow from this decision.

### D14. Testing
- **Unit:** Vitest 5.x in Node. Covers:
  - schemas and error codes, normalization, enums against the SQL `CHECK` constraints
  - i18n key parity, route-map completeness, CSV escaping (formula-injection prefixes `= + - @ \t \r`)
  - email templates in all locales, the CSP header builder, content-status rules
- **Integration:** ~~`@cloudflare/vitest-pool-workers` runs handlers in workerd~~ (superseded by amendment A1). Vitest 5 in Node drives the real handlers against a real workerd D1 from wrangler's `getPlatformProxy`, with migrations applied by `wrangler d1 migrations apply --local`, plus a `wrangler pages dev` test of the real `functions/` tree. Email goes to the `mock` transport. Covers:
  - both forms end to end at the handler level: limiter, honeypot, origin
  - Access JWT verification against a test JWKS
  - the role matrix, audit writes, retention purge and CSV export
- **E2E:** Playwright 1.6x (1.64.0, projects and CI status in A4.2) against the built site served by `wrangler pages dev dist`, so the real `_headers`, `_redirects` and Functions are in play, with local D1, the mock mail server and the dev Access proxy. Covers:
  - both forms in SK, CS and EN, including the no-JS fallback, validation errors and recovery
  - admin flows
  - zero CSP violations and zero requests to other origins
- **Accessibility:** `@axe-core/playwright` on every page in 3 locales, at 360, 768 and 1280 px. It fails on serious or critical issues.
- **Performance and SEO:** Lighthouse CI (`@lhci/cli` 0.15) on built pages, with budgets of performance ≥ 90, accessibility ≥ 95 and SEO ≥ 95. A build-time link checker and a hreflang reciprocity checker run on `dist/`.

### D15. Toolchain
- **Node:** Node.js 24 LTS ("Krypton"), in `.nvmrc` and `engines: ">=24 <25"`. Astro 7 needs Node 22.23.4 or later.
- **Dev-machine constraint (L0, 2026-10-24):** the dev machine has Node 22.22.1 and corepack 0.24, which cannot run pnpm 12. L0 therefore sets `engines.node` to `">=22.12"`, `.nvmrc` to `22` and `packageManager` to `pnpm@10.34.6` (brief owner decisions). Revisit when the machine is upgraded.

- **wrangler:** 4.x as a devDependency.
- **Lint and types:** TypeScript strict, ESLint plus `astro check`, and Prettier.

## Amendments

### A1. Integration tests without `@cloudflare/vitest-pool-workers` (L5b sign-off, 2026-10-24; amends D14)
- **Context:** every `@cloudflare/vitest-pool-workers` release up to the latest, 0.23.0 (2026-10-07, npm registry), declares peers `vitest ^4.1.0`, `@vitest/runner ^4.1.0` and `@vitest/snapshot ^4.1.0`. The repo is on Vitest 5.0.3 (D14).
- **Options:** (a) downgrade the whole repo to Vitest 4; (b) a second Vitest 4 install only for integration tests; (c) Vitest 5 in Node with `getPlatformProxy` for a real workerd D1, migrations applied by the real `wrangler d1 migrations apply --local` (`tests/integration/global-setup.ts`), plus a `wrangler pages dev` test of `functions/` routing and middleware.
- **Decision:** (c), as built in `tests/integration/`.
- **Consequences:**
  - Handlers run in Node, not workerd. Only the D1 binding is real. Runtime differences (Web Crypto, `fetch`, streams) are covered by the `wrangler pages dev` test and by the L6 and L7 e2e suites, which run on `wrangler pages dev dist`.
  - Migrations are tested through the same command used in deploys, which is stronger than `applyD1Migrations`.
  - Revisit when a pool-workers release supports Vitest 5.
  - `pnpm test:integration` joins the CI gate now that L5b exists (plan §1).

### A2. Recipient limit skips the confirmation instead of rejecting (L5b sign-off, 2026-10-24; amends D6 item 3)
- **Context:** L5b answered 429 after validation when the per-recipient limit was hit, so the submission was lost.
- **Options:** (a) 429 and drop the submission; (b) store it, skip the sender confirmation, still notify the admin.
- **Decision:** (b). The recipient counter counts confirmations actually queued. Over the limit, the `sender_confirmation` delivery row is `skipped` with `last_error_code = 'recipient_limit'`, and the response is the normal success. The per-IP limiter (D6 item 3) still answers 429.
- **Consequences:** a real parent who submits several forms in a day is never refused; an attacker learns nothing about the target address and still cannot make it receive more than the limit. Storage abuse stays bounded by the per-IP limiter.

### A3. Admin API contract and routing (L5b sign-off, 2026-10-24; refines D7 and D8)
- **Decision:**
  - The admin contract is `src/shared/admin-api.ts`, additive to the frozen form contract.
  - Routing is one auth middleware plus a catch-all with the route table and permission matrix in `src/server/admin/router.ts` (`docs/architecture.md` §5).
  - A search term travels only in the JSON body of `POST /api/admin/records/search`; `GET /api/admin/records` rejects `q`. The search is a read, so it is exempt from "mutations only" but still meets the D7 checks for `POST` (`application/json`, `Origin`, `Sec-Fetch-Site`).
  - Errors add 401 `unauthorized`, 403 `origin` and `forbidden`, 404 `not_found` and 409 `conflict` (`docs/architecture.md` §4.3).
- **Consequences:** L7 builds only against `src/shared/admin-api.ts`. Changing it after L7 starts needs a coordinated PR (plan §5 risk 4). The remaining L5b decisions are in `docs/architecture.md` §4.6.

### A4. Island mounting, e2e tooling and Trusted Types (L6 and L7 sign-off, 2026-10-24; amends D2, D13 and D14)

**A4.1 Island mounting.**
- **Context:** Astro's island runtime (`client:*` directives) emits `<style>astro-island,astro-slot,astro-static-slot{display:contents}</style>` before the first island, plus inline bootstrap `<script>`s. `style-src 'self'` forbids the style, and `tools/build-headers.mjs` rejects it. The two lanes solved this in two ways:
  - **L6 (forms):** no Astro directive. `src/pages/_forms/ContactPage.astro` and `EnrolPage.astro` render the Preact component at build time inside `<div data-island="contact|enrol" data-props="…">`, which is a complete no-JS form. One external module per form (`src/islands/forms/mount-contact.ts`, `mount-enrol.ts`, both through `mountIsland()` in `src/islands/forms/mount.ts`) calls `hydrate()` with the same props. The result has no inline script or style and no hash. Hydration is eager on load, not on visibility. `@preact/signals` is not used; the islands use plain hooks.
  - **L7 (admin):** `<AdminApp client:only="preact" />` in `src/pages/admin/index.astro`, so the Astro runtime is used. The `stripIslandStyle` build hook in `astro.config.mjs` removes that exact inline style literal after the build. It fails closed: if Astro changes the literal, the hook stops matching and build-headers rejects the inline style. The `display:contents` rule ships in `src/islands/admin/admin.css`. The runtime's two inline scripts are the only inline-script hashes in today's build (only `dist/admin/index.html` contains `<script>`). They are inserted into the `/*` policy, so every public page also allows them.
- **Options:** (a) keep both patterns; (b) make the L7 pattern (Astro directives plus the strip hook) canonical; (c) make the L6 pattern (build-time render plus an external mount module) canonical and move the admin to it.
- **Decision:** (c). **Canonical for every future island** (FAQ search, consent banner): no `client:*` directive. Render at build time inside `<div data-island="<name>" data-props="…">`, then hydrate from one external module through a shared mount helper. A client-only island such as `AdminApp` uses the same helper with `render()` into an empty `data-island` element instead of `hydrate()`. If an enhancement needs no component state, prefer a plain TypeScript module over a Preact island. FAQ search (`docs/design/system.md` §6.7) is that case: it filters static `<details>` markup, so it should stay within the 10 KB content-page budget.
- **What must move** (follow-up for frontend-dev, which owns `src/islands/**`, and developer, which owns `astro.config.mjs`):
  1. Move `mountIsland()` from `src/islands/forms/mount.ts` to a shared place (`src/islands/mount.ts`) and add a `render` mode.
  2. Mount `AdminApp` with `src/islands/admin/mount.ts` from a `<script>` module tag in `src/pages/admin/index.astro`, and remove `client:only`.
  3. Remove the `stripIslandStyle` hook and the `astro-island` rule in `admin.css`.
  4. devops: lower the inline-script hash limit in `tools/lib/headers.mjs` from 6 to 0, so any executable inline script fails the build, and drop `{{INLINE_SCRIPT_HASHES}}`.

  Until step 2 lands, the strip hook stays. If any page other than `/admin/` ever emits `astro-island`, the `display:contents` rule must first move to `src/styles/global.css` (web-designer), because `admin.css` loads only on `/admin/`.
- **Consequences:** progressive enhancement is uniform. Every island has server-rendered HTML that works without JS, except the admin, which is JS-only by design (D8). The CSP never needs hashes. One less build hook depends on an Astro-internal string. Losing `client:visible` and `client:idle` deferral is acceptable: the module scripts are deferred, and the size budgets in D2 still apply. D2's directive list and `@preact/signals` are superseded by this amendment.

**A4.3 Trusted Types on `/admin/*`.**
- **Context:** L7 ran `tests/e2e/admin/quality.spec.ts` with `require-trusted-types-for 'script'` added as a second policy on the `/admin/` document. It got zero violations across the list, detail, status change and audit views. The app creates no Trusted Types policy.
- **Decision:** enforce `require-trusted-types-for 'script'` on `/admin/*`. Do not add a `trusted-types` directive: it only allow-lists policy names, and no policy is created. This replaces the "trial in Phase 7" in D13.
- **Caveats:**
  - Only Chromium was tested. Browsers without Trusted Types support ignore the directive, so it is defence in depth, not a gate.
  - The trial header was injected by Playwright on top of what `wrangler pages dev` sends. Wrangler's `_headers` emulation is not proof of production behaviour, so verify on the preview with `curl -I`.
  - Do not rely on how a second `Content-Security-Policy` from the `/admin/*` rule combines with the `/*` one. Use `! Content-Security-Policy` in `/admin/*`, as `/cms/*` already does, followed by the full public policy plus `; require-trusted-types-for 'script'`. That gives one policy, and the result does not depend on how Pages merges headers.
- **Follow-up (devops; not done by this amendment):** add that block to `config/headers.template`, teach `tools/lib/headers.mjs` and `tools/check-dist.mjs` to assert that `/admin/*` sends exactly one CSP containing `require-trusted-types-for 'script'` and that no other path sends it, and replace the route override in `quality.spec.ts` with an assertion on the served header.

**A4.4 Consequences for D13.** Hashes are a fallback, not the plan. After A4.1 step 4, the build fails on any executable inline script. JSON-LD stays exempt.

**A4.5 No-JS failure message (known gap).**
- **Context:** on a no-JS failure, `src/server/handlers/public-form.ts` redirects (303) to the form page with `?error=1`. The page is static and has no script, so it cannot read the query, and `docs/architecture.md` §4.1's promised "generic localized message" never appears.
- **Options:** (a) the server redirects to `?error=1#form-error`, and the form page always renders a hidden notice `<div id="form-error" tabindex="-1">` that CSS shows with `#form-error:target`. The backend lane changes the redirect; frontend-dev and web-designer own the notice markup and CSS. (b) Amend §4.1 to say that the message appears only with JS.
- **Decision:** (a). It is one line on the server plus a static notice. It needs no JS and no CSP change, and the fragment also scrolls the notice into view. Keep `?error=1` for logs. Field-level errors stay JS-only. Without JS, the browser's native constraint validation (`required`, `type`, `maxlength`) is the first line of defence. Until (a) ships, the gap stays open and L10 tests for it.

## Gaps: parts of the brief this stack cannot meet as written, and the fix

1. **§14 "administrators can update without programming": CMS edits are not live.** A merge has to be followed by a deploy, and `cf-pages-deploy` requires one approval per deploy.
   - **Fix:** Sveltia's editorial workflow opens PRs. A developer or the owner merges, and the owner approves a deploy.
   - **Option (owner):** a standing approval for Pages Git integration, auto-building `main` to production, which removes the wait.
2. **§14 "application statuses" in the CMS.** The status set is an enum in code and in D1 `CHECK` constraints. **Fix:** staff change statuses in the admin, and status labels are editable translations. Adding a new status is a code change.
3. **§7 retention deletion needs a scheduler.** Pages has no cron (F2).
   - **Fix, v1:** an admin "Retention" view lists records past `retain_until` and deletes them in bulk with an audit entry. An overdue banner appears on the admin home.
   - **Phase 8 option:** a separate ~50-line Worker `workers/maintenance` with a daily cron bound to the same D1 database. It needs its own Workers approval.
4. **§10 rate limiting.** There is no Rate Limiting binding on Pages (F2). **Fix:** the D1 limiter plus a WAF rule (D6).
5. **§7 "role-based authorization" from identity.** **Fix:** an Access gate plus the D1 role table (D8). IdP groups are an optional later step.
6. **§5.6 "optional map".** A third-party map embed breaks the strict CSP and loads tracking before consent. **Fix:** a static map image rendered at build time from an owner-supplied or licensed asset, plus an outbound "Open in maps" link.
7. **Astro adapter dropped Pages support (F1).** **Fix:** no adapter (D1), with a documented migration path to Workers if Pages is retired.
8. **§10 Next.js, React, shadcn, Motion and Prisma** are replaced by D1–D4 and D10. Every requirement those tools served is still met.
